# Contributing To Forge

This document explains how to work effectively in the Forge repository.

## First Things To Read

If you are orienting yourself for the first time, read these in order:

1. [README.md](./README.md)
2. [ARCHITECTURE.md](./ARCHITECTURE.md)
3. [cmd/forge/main.go](./cmd/forge/main.go)
4. [internal/bootstrap/runtime.go](./internal/bootstrap/runtime.go)
5. [internal/runtime/chat.go](./internal/runtime/chat.go)
 6. [internal/react/loop.go](./internal/react/loop.go)

## Repository Shape

Important top-level areas:

- [cmd/forge/main.go](./cmd/forge/main.go): CLI entrypoint
- [internal/bootstrap/](./internal/bootstrap): config loading, model discovery, provider routing
- [internal/runtime/](./internal/runtime): chat and session assembly
- [internal/react/](./internal/react): core React loop, session state, tool selection
- [internal/agent/](./internal/agent): agent prompts, legacy dispatch path, tool implementations
- [internal/agent/tools/](./internal/agent/tools): tool implementations
- [internal/tui/](./internal/tui): Bubble Tea frontends and UI models
- [internal/llm/](./internal/llm): driver interfaces, retries, events, usage
- [internal/llm/drivers/](./internal/llm/drivers): provider-specific implementations
- [internal/session/](./internal/session): pass-based improvement runner
- [internal/config/](./internal/config): config schema and persistence
- [docs/](./docs): repo documentation

## Local Setup

Minimum:

```bash
just build
just test
```

These recipes require `just` to be installed and available on your `PATH`.

For hook-compatible development, install the tools listed in [LOCAL_TOOLING.md](./LOCAL_TOOLING.md).

Recommended:

```bash
just check
```

The raw Go equivalents remain available when you need to see the underlying commands:

- `go build -o ./bin/forge ./cmd/forge`
- `go test ./...`

## Pre-Commit Hooks

This repository uses local hooks from [.pre-commit-config.yaml](./.pre-commit-config.yaml).

Important checks include:

- risky filename detection
- merge conflict marker detection
- trailing whitespace detection
- private key marker detection
- `gitleaks`
- `gofmt`
- `goimports`
- `go vet`
- `golangci-lint`
- `govulncheck`

If your commit fails, read the hook output directly. The most common issues are formatting drift, lint failures, or missing local tooling.

For a hook-compatible local check before committing, run `just pre-commit`.

## Recommended Workflow

For code changes:

1. read the relevant runtime path first
2. add or update tests before changing behavior
3. keep changes scoped to one concern
4. run targeted tests
5. run `just build`
6. run `just test`

Practical rule:

- if you change provider behavior, start in bootstrap and drivers
- if you change root CLI behavior, start in [cmd/forge/main.go](./cmd/forge/main.go) and verify `forge`
- if you change chat behavior, start in runtime, agent, and TUI together
- if you change session/pipeline behavior, start in runtime/session and `internal/session`

For provider/model changes, always re-check:

- [internal/bootstrap/runtime.go](./internal/bootstrap/runtime.go)
- provider-specific driver tests
- model picker behavior in [internal/tui/chatmodel.go](./internal/tui/chatmodel.go)

For chat behavior changes, always re-check:

- [internal/runtime/chat.go](./internal/runtime/chat.go)
- [internal/react/loop.go](./internal/react/loop.go)
- [internal/tui/chatmodel.go](./internal/tui/chatmodel.go)

## Adding A Tool

Tools live in [internal/agent/tools/](./internal/agent/tools).

Typical steps:

1. implement the tool
2. register it in `registerTools(...)` in [internal/runtime/chat.go](./internal/runtime/chat.go)
3. decide whether it is prompt-core or prompt-hidden
4. update tests
5. update tool group lists and `allowedToolNamesForSnapshot` in [internal/react/loop.go](./internal/react/loop.go) to control when the tool appears in native tool definitions

Also re-check the system prompt generated by [internal/agent/system.go](./internal/agent/system.go), because prompt-visible vs hidden tool behavior affects what the model can see.

## Adding Or Changing A Provider

Provider work usually touches several layers:

- config and stored credentials
- provider auth flow
- driver implementation
- model discovery
- bootstrap routing
- provider picker / model picker behavior
- tests

Common files:

- [internal/auth/store.go](./internal/auth/store.go)
- [internal/bootstrap/runtime.go](./internal/bootstrap/runtime.go)
- [internal/llm/drivers/](./internal/llm/drivers)
- [internal/tui/chatmodel.go](./internal/tui/chatmodel.go)

Do not treat model naming, auth, and request shape as separable by default. In practice they often need to change together.

When debugging provider issues, verify all of these before assuming the provider is broken:

- resolved provider ID
- model canonicalization
- live discovery vs fallback catalog
- auth source
- request mode / request path
- error distillation in the TUI

## Multi-Agent Work

Multi-agent behavior is not just a prompt change. It crosses:

- tool selection in [internal/react/loop.go](./internal/react/loop.go)
- delegation in [internal/agent/subagent.go](./internal/agent/subagent.go)
- runtime setup in [internal/runtime/chat.go](./internal/runtime/chat.go)
- chat rendering in [internal/tui/chatmodel.go](./internal/tui/chatmodel.go)

If you change delegation behavior, verify both:

- tool-pane audit detail
- main-pane chat summaries / recent activity

## Documentation Expectations

If behavior changes in any of these areas, update docs in the same change:

- user-facing commands or setup: [README.md](./README.md)
- architectural behavior: [ARCHITECTURE.md](./ARCHITECTURE.md)
- build workflow: [BUILD.md](./BUILD.md)

For larger feature work, also check whether there is already a spec or plan under [docs/superpowers/specs/](./docs/superpowers/specs) or [docs/superpowers/plans/](./docs/superpowers/plans).

## Testing Guidance

Prefer targeted tests while iterating, then run the full suite before committing.

Examples:

```bash
just test-pkg ./internal/agent
just test-pkg ./internal/bootstrap
just test-pkg ./internal/tui
```

For narrower test selection, use the raw Go command directly:

```bash
go test ./internal/agent -run TestAgentRunDoesNotRetryShortFinalAnswer
go test ./internal/bootstrap -run TestCanonicalAnthropicModel
go test ./internal/tui -run TestChatModelModelsOverlayLeadingDigitStartsSearch
```

Final verification:

```bash
just check
```

If a bug reproduces only in chat mode, prefer adding a focused regression test near:

- [internal/react/loop_test.go](./internal/react/loop_test.go)
- [internal/bootstrap/resolve_test.go](./internal/bootstrap/resolve_test.go)
- [internal/tui/chatmodel_test.go](./internal/tui/chatmodel_test.go)
- provider-specific driver tests under [internal/llm/drivers/](./internal/llm/drivers)

## Security And Secrets

This repository has strict handling rules for secret-bearing paths and auth material.

Before touching auth or config code, read:

- [AGENTS.md](./AGENTS.md)

Key rule: do not print or copy secrets into code, docs, logs, fixtures, or commits.
